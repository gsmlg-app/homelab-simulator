# Cloud Center 第一阶段实施计划

**项目：** `gsmlg-app/homelab-simulator`

**计划日期：** 2026-10-17

**审阅基线：** `main` / `89b799c846e274ec5a2da143a1cc037a5f07bee1`

**建议仓库路径：** `docs/cloud-center/implementation-plan.md`

**状态：** 已实施并通过范围内离线自动化验收及 macOS Debug 构建，可准备明确标注限制的源码预发布；完整原生手动流程与三家真实账号验证仍待完成。当前 AC01–22 结果、证据与限制见[验收报告](validation-report.md)；这不表示已发布或完成生产接入。

## 1. 目标与完成边界

交付一个可以真实使用的云监控入口：用户进入 **Cloud Center（云中心）** 房间，走到 Cloudflare、AWS 或 GCP 控制台前，主动交互打开 Flutter 面板，查看对应账号的资源清单、资源使用和费用。房间内另有一个跨云费用看板。

核心闭环：

`进入房间 → 靠近控制台 → 主动打开 → 查看真实数据及其覆盖范围 → 关闭面板 → 继续移动`

后台采集独立于角色、房间、面板和客户端运行。用户离开云中心或关闭应用，不应停止已经部署的后台采集。

### 必须交付

- 一间云中心、三个厂商控制台、一个费用总览看板、可返回原房间的出口。
- 键盘、现有手柄路径、触屏三种交互；移动端不能只显示键盘提示。
- 原生 Flutter 详情面板，不嵌入厂商网站，不通过网页自动化抓账单。
- 三家真实只读适配器：费用接入，以及本计划限定的资源与指标接入。
- 费用周期、币种、费用口径、权限范围、缺失数据及更新时间可见。
- 单用户自托管聚合后端；可配置多个连接、账号或项目；默认先配置每家一个连接。
- 明确标注的离线演示模式、可重复的自动化测试、真实账号验证入口。
- 简单的应用内预算阈值提示，以及安装、配置和验收文档。

### 不属于本阶段

不开发新云厂商、Kubernetes/Prometheus 通用监控、资源关系拓扑、逐资源游戏图标、3D 场景、多人游戏、角色和商店扩展、通用告警平台、外部通知、智能费用预测、自动汇率换算、完整 FinOps/FOCUS 实现、云资源创建/停止/删除、云端预算修改、付款、发票 PDF 下载或完整资源级成本分摊。

**费用范围不能被资源详情的支持列表截断。** 费用数据源返回的其他服务仍要计入相应费用视图，使用“其他服务”或“未分配费用”展示。第一版不能宣称覆盖所有资源类型或所有账单项目。

## 3. 交互设计

### 3.1 房间与控制台

新增 `RoomType.cloudCenter`，使用固定布局模板。根据当前房间尺寸布置三个控制台、一个费用看板及门，不硬编码一套与现有坐标系统不一致的尺寸。

控制台是**数据入口**，不是云资源本体。每个控制台绑定厂商入口，面板内部再选择连接、账号或项目。新增第二个 AWS 账号不需要新增游戏对象。

建议新增不可变 `CloudConsoleModel`，放在游戏领域层：`id`、`roomId`、位置、尺寸、类型、目标引用。目标使用明确的类型区分厂商入口和费用总览，避免用任意字符串解析业务含义。

使用稳定的房间、门和控制台 ID，提供幂等初始化：重复登录、加载旧存档和重复迁移都不能产生第二间云中心。已有布局无法容纳入口时，显示明确的入口配置状态或使用既有房间导航能力；不得覆盖原设备、删除门或重置角色。

将控制台占用区域加入碰撞判断，保留可达的交互格及出口路径。首版不实现远距离自动寻路；触屏使用现有移动能力到达交互区域，再点击“打开”。

### 3.2 交互状态

采用单一交互状态流：`探索 → 存在可交互目标 → 面板打开 → 返回探索`。靠近只高亮和显示提示，**不得自动弹出面板**。

- 键盘：沿用移动键，`E` 打开，`Esc` 返回面板上一级或关闭。
- 手柄：沿用移动输入，确认键打开，返回键返回/关闭。
- 触屏：显示真实可点击的交互按钮；点击附近控制台也可触发同一意图。
- 多个目标同时满足条件时，使用统一的距离与稳定 ID 排序规则；不能让门、终端、控制台各自覆写当前目标。

面板打开时统一屏蔽角色移动、场景放置、商店快捷键和穿透点击。文本框输入不能移动角色；关闭面板后清理持续按键状态并恢复场景焦点。

同一时刻只允许一个云面板。切换房间、退出角色、切换演示/真实模式时关闭面板并取消相关 UI 请求。采集任务不属于面板生命周期，不能一起被取消。

### 3.3 面板与状态显示

桌面/平板使用侧边面板；窄屏使用全屏面板。两种布局复用同一内容和导航状态。使用现有主题、国际化与组件规范。

| 页面 | 必须内容 |
|---|---|
| 厂商总览 | 连接/账号/项目选择、当前费用、周期、币种、预算、资源数及统计范围、同步状态。 |
| 费用 | 指定日期范围的趋势、按服务拆分、历史可用周期、费用口径及包含/排除项。 |
| 资源 | 第一批支持类型的分页列表、服务与区域筛选、搜索、资源详情。 |
| 用量 | 有明确单位、时间区间、聚合方法的数据；可从服务或资源详情进入。 |
| 连接状态 | 配置缺失、认证失败、缺权限、功能不支持、等待账单导出、上游延迟、重试结果。 |
| 总费用看板 | 可比较的相同时间窗口、按币种分开的金额、覆盖厂商列表、缺失与未分配费用。 |

把三类状态分开：数据连接/同步状态、数据新鲜度、预算状态。资源运行状态另行展示，不从费用大小或同步结果推断资源是否故障。不能只有一个“正常/异常”灯。

总看板不得把各厂商不同长度的“当前账期”直接相加。默认使用明确的日历日期范围；厂商面板另保留原生账期。无法映射到同一窗口的数据不硬分摊，单列并说明。应用展示时区与源账期时区分开保存；不能按手机当前时区重新切割已发布的费用桶。

## 4. 架构与包边界

### 4.1 总体结构

`厂商只读接口 → Elixir 聚合后端 → PostgreSQL → 自有 HTTP API → Flutter 云状态层 → Flame 摘要 / Flutter 详情`

第一版采用同仓库单体后端 `services/cloud_monitor/`：独立 Mix 项目，Phoenix API-only、Ecto/PostgreSQL、OTP supervision。不创建微服务，不修改 Backplane 或其他仓库，不因后端设计而迁移现有 Flutter 项目。

领域变换采用纯函数：解析后的费用归一化、数据新鲜度判断、预算计算、场景摘要投影与交互目标选择。HTTP、数据库、时钟、密钥读取和任务调度留在边界。不要围绕每个资源创建常驻进程，也不建立通用插件框架。

### 4.2 建议新增目录

| 路径 | 职责 |
|---|---|
| `app_lib/cloud/` | 与 Flame 无关的云 DTO、查询参数、不可变值对象、Repository 契约。 |
| `app_lib/cloud_client/` | 自有后端 HTTP 客户端、演示实现、请求取消与错误映射。 |
| `app_bloc/cloud_center/` | 当前数据、查询与加载状态、面板导航、连接选择。 |
| `game_objects/cloud_center/` | 控制台及看板渲染、交互高亮、摘要更新。 |
| `game_widgets/cloud_center/` | Flutter 面板、表格、趋势、配置与状态页。 |
| `services/cloud_monitor/` | 真实适配器、采集调度、持久化、聚合、预算和 API。 |
| `docs/cloud-center/` | 实施计划、API 契约、厂商接入说明、验收报告。 |

更新根 workspace 和确实需要这些包的依赖。包名遵循仓库习惯。新目录是建议落点；若 HEAD 已有等价模块，直接扩展，不建立平行实现。

`GameBloc` 管游戏世界；云数据不要整体塞入 `GameModel`。`WorldBloc` 管场景交互；不能成为账单缓存。云状态层输出小型控制台摘要，Flame 不能遍历所有费用记录来计算总额。

### 4.3 数据模型

| 模型 | 必须表达的语义 |
|---|---|
| `CloudConnection` | 厂商、显示名称、服务端凭据引用、允许范围、各数据集能力及同步状态。 |
| `BillingScope` | 付款范围、资源账号/项目、父子关系；查询范围不等于游戏房间。 |
| `CloudResource` | 厂商稳定 ID、账号/项目、类型、区域、名称、标签、观测时间；身份不依赖连接显示名。 |
| `UsageSample` | 指标、单位、区间、粒度、资源或服务归属、聚合方式、来源。 |
| `CostRecord` | 来源、范围、服务、可空资源 ID、时间区间、币种、十进制金额、口径、原始分类及覆盖元数据。 |
| `DatasetStatus` | 能力、最近尝试、最近成功、来源时间、实际观测区间、完整性、原因码。 |
| `BudgetRule` | 明确的范围、币种、周期、费用口径、金额和阈值。 |
| `ConsoleSummary` | 场景需要的金额标签、周期、预算状态和数据状态，不含凭据或完整明细。 |

不要沿用把 `actual/estimated/forecast/tax/credit` 混在一个枚举的模型：

- **记录性质**：来源已报告的费用、预测；首版不生成预测。
- **费用分类**：使用费、订阅、税、抵扣、退款、调整、未知。
- **费用口径**：例如 AWS 的 UnblendedCost 或来源原有口径。
- **最终性**：保留来源的估算标志；没有最终性证据时不能写“最终账单”。

内部费用查询统一区间语义为左闭右开 `[start, end)`；各厂商的原生区间格式在适配器边界转换并保留原始值。为月末、跨年、非月初账期和时区变化增加测试，不把来源的包含式结束时间原样当排除式结束时间使用。

金额在后端使用 Decimal/PostgreSQL numeric，API 用十进制字符串传输，客户端避免二进制浮点聚合。JSON 数字和 BigQuery 原始浮点数据在适配边界处理，记录源精度；不能声称恢复上游已损失的精度。只在显示时舍入。

## 5. 后端采集与费用正确性

### 5.1 调度与持久化

区分资源清单、运行指标、费用三个数据集，独立记录成功与失败。一个产品指标缺权限不能清空整个厂商费用。

第一版使用单实例调度器与有界 Task.Supervisor，并在数据库保存任务状态、重试和到期时间。启动时恢复未完成任务；每个“连接 + 数据集”最多一个活动任务。不要开发分布式任务平台。

建议起始默认值：资源清单每 30 分钟、已启用运行指标每 15 分钟、Cloudflare/AWS 费用每日、GCP 费用每 6 小时；均为本产品的可配置默认值，不代表上游更新承诺。存储类日指标遵循其来源频率，不用分钟轮询伪造实时性。运行指标只查询已配置范围，设置资源数量、查询次数及历史窗口上限。

所有面板查询读取本地结果；打开面板不直接发云 API 请求。手动同步走去重任务、冷却和配额，返回任务状态。错误使用有限重试、退避及来源 Retry-After；缺权限和配置错误不进行密集重试。

### 5.2 原子提交与去重

- 所有分页抓取、解析和校验成功后，才原子发布对应范围的新快照及 revision。
- 部分页失败时保留旧数据并标记失败/过期，不能用半份快照替换全量数据。
- 聚合快照按“规范化查询范围 + 数据粒度 + 分组键 + 币种 + 口径”替换，不每次累加累计金额。
- 汇总结果和下钻结果是不同视图，不可作为同一批费用再次相加。
- 同一个 AWS 付款账号与其子账号、同一个 GCP Billing Account 与项目明细不能重复计费。
- 删除游戏对象、角色或连接展示绑定不删除财务历史；清理历史只能通过独立且明确的保留策略。
- 资源缺少稳定匹配关系时保持 `resourceId = null`；不得通过同名资源或平均分摊伪造资源成本。
- 相同 BillingScope 被多个连接配置时，确定一个权威费用来源，其他为别名/备用，不双计。

原始响应仅在必要的脱敏诊断范围内保留；缓存按查询数、资源数和保留时间设上限，失败记录同样执行清理策略，不让轮询产生无限历史。

初始回填默认本期及前两个可用月份，范围可配置且设上限。费用同步重读本期和上期以接收调整，提供明确的更早周期重同步入口；不能承诺老账单永不变化。

### 5.3 新鲜度和完整性

分别保留 `lastAttemptAt`、`lastSuccessAt`、`sourceAsOf`、观测到的区间及完整性。请求时间、请求的结束时间、最大一条记录时间都**不能自动等价于“数据完整覆盖到这里”**；来源没有 watermark 时允许未知。

状态至少包括：未配置、等待数据、已知空结果、部分数据、可用、过期、缺权限、认证失败、不支持、限流/失败。空结果只有在权限、范围和数据语义明确时才可显示为零。

区分“采集超过预期未成功”和“来源账单尚未追上当前时间”。同步成功只能刷新采集成功时间，不能把仍旧延迟的费用伪装成当前费用。

## 6. 三家适配器的最低范围

费用覆盖和资源详情覆盖分开声明。以下接口能力参考 [S1–S9]；实现时验证当时官方版本、请求方法、分页、权限和真实返回结构。不得凭文档名字虚构通用账单接口。

### 6.1 Cloudflare

**费用：** 使用适用于账号的 Billable Usage 接口。当前参考文档有 Alpha 和方法迁移标记，需封装版本差异并检测授权能力。官方给出的费用行按产品和 charge period 返回；`ContractedCost` 与 `CumulatedContractedCost` 不能重复求和。更新频率和账期能力以来源为准。[S1, S2]

固定套餐订阅不能假定已经包含在使用费中。可访问的账单历史作为独立视图；不要把历史发票总额再加到当期使用费。某类费用无法接入时明确列为未覆盖，不估算出一个“完整账单”。保留原生账期。[S3]

**资源：** Zones、Workers、R2 buckets。

**指标：** Workers 请求/错误量；R2 已存储容量及支持的操作量；Zone 请求统计作为能力项。使用各产品官方指标 API/GraphQL，不从费用推导实时流量。GraphQL 数据集、粒度和权限按账号能力检测。[S7]

**验收：** 多产品、累计与区间费用共存、分页、部分权限、不可用字段、非月初账期均有测试；不存在真实授权时适配器仍具有真实 HTTP 实现和契约测试。

### 6.2 AWS

**费用：** 使用 Cost Explorer `GetCostAndUsage`，首版固定并展示 `UnblendedCost` 口径。每日粒度、服务及账号范围，正确处理分页和 `Estimated`。每个请求最多两个分组维度；更多下钻拆成独立查询视图，不能相加。UsageQuantity 必须按同质用量类型和单位处理。[S4]

设置查询缓存和调用预算，不能每个客户端分别轮询 Cost Explorer。官方说明其查询计费且费用更新并非实时。[S5]

**资源：** EC2 instances、EBS volumes、S3 buckets。Lightsail 留待后续，不要求补齐所有 AWS 服务详情。

**指标：** EC2 CPU 与网络，EBS 支持的读写指标，S3 日存储容量与对象数；不自动启用付费 request metrics。日指标不能显示为分钟实时值。[S8]

认证使用已有只读身份/角色与短期凭据能力；实际签名、会话 token 和区域处理通过可验证的库实现。只遍历明确配置的账号与区域。没有 Cost Explorer 资源级依据时，服务费用可用而单资源费用显示“不可归属”，不能平均分给 EC2 实例。

### 6.3 GCP

**费用：** 从已配置的 Cloud Billing BigQuery export 查询。兼容 Standard 与 Detailed 的共同字段，Detailed 提供的资源维度属于附加能力。账单账号、资源项目、执行 BigQuery 查询的项目必须分别配置。不得把账号管理 API 当费用明细 API。[S6]

将 credits 在每条源记录内聚合后再计算净额，避免直接展开数组导致 cost 重复。保留 `invoice.month`、usage 区间、调整及 export 时间，不能用 usage 月份替代开票月份。使用 NUMERIC 等受控十进制计算并以字符串返回结果。[S6]

按限定日期和分区过滤，设置查询字节预算、超时与分页。export 尚未配置、权限不足、表为空但仍在等待导出、来源延迟都要有独立状态。不能自动开通导出或创建云资源。官方不保证统一的导出延迟。[S6a]

**资源：** Compute Engine、Cloud Storage、Cloud Run；通过官方资源 API或现有 Asset Inventory 权限获取。范围不完整时在资源数旁标注。

**指标：** GCE CPU、Cloud Run 请求量、Cloud Storage 容量等已有 Monitoring 指标，精确指标名称、resource labels、聚合与采样频率按官方描述符验证。[S9]

## 7. API、缓存与凭据

### 7.1 自有 API

先形成 `docs/cloud-center/api-contract.md`。可以采用以下路由职责，不要求为了名称改写已有等价接口：

| 接口 | 职责 |
|---|---|
| `GET /v1/cloud-center/overview` | 已配置厂商摘要、按币种分开的费用、比较窗口与覆盖状态。 |
| `GET /v1/connections` | 已配置连接和能力，不含任何云密钥。 |
| `GET /v1/connections/{id}/overview` | 单连接的摘要与各数据集状态。 |
| `GET /v1/connections/{id}/costs` | 有上限的日期范围、费用口径、分组与分页。 |
| `GET /v1/connections/{id}/resources` | 按服务/区域/项目筛选和分页。 |
| `GET /v1/resources/{id}/usage` | 有界的指标查询，不触发无约束回源。 |
| `POST /v1/connections/{id}/sync` | 对本应用提交去重同步任务；返回 202 和 job ID。 |
| `GET /v1/sync-jobs/{id}` | 任务状态、错误码及可公开的诊断。 |
| 应用内预算接口 | 只读写本应用预算，不修改云厂商预算或资源。 |

响应包含 schema version、查询上下文、revision、来源时间与完整性。分页 cursor 绑定筛选条件和 revision；旧 revision 不可继续读取时返回明确错误并重拉。新旧页面不能悄悄拼成一张不一致的列表。

首版客户端对自有后端使用有界 HTTP 轮询，不要求 WebSocket/SSE。建议前台每 60 秒检查摘要，手动同步任务可以短周期检查；进入后台暂停客户端轮询，返回时先读缓存再刷新。服务端采集继续运行。用请求序号/查询 key 忽略过期响应，防止切换厂商后慢响应覆盖新面板。

### 7.2 本地缓存与配置

Drift 保存后端连接信息、选择偏好、有界摘要/列表缓存及 schema version。新增迁移，不清空既有游戏存档。缓存必须以“后端实例/授权上下文 + 演示或真实模式 + 查询参数”隔离；退出真实连接清除敏感缓存和会话。

云密钥只在后端使用，首版通过部署配置的环境变量或只读 secret 文件引用配置。Flutter 只保存本应用的访问凭据，并复用 `app_lib/secure_storage`。游戏角色选择不是后端鉴权。

只读指“不改变云资源”。应用自身的同步任务、预算和偏好允许写入。BigQuery 查询可产生必要的查询 job，但只能执行限定查询，不能夹带 DDL/DML。

远程连接使用 TLS；开发环境只对明确的 loopback 例外放行。所有日志、错误响应、fixture、截图和 release 附件都不得包含真实 token、私钥或未脱敏账单。只实现必要的认证、范围限制、密钥脱敏及针对性测试，不扩展为无关安全审计。

## 11. 完成、阻塞与发布

报告中必须区分：

1. **代码完成**：范围内代码、配置说明和自动化测试完整。
2. **真实接入已验证**：使用实际授权完成具体服务、费用与指标 smoke test。
3. **外部条件待配置**：缺少凭据、权限、费用导出或平台构建环境；列明受影响验收项。

不能把第 3 项写成“全功能通过”，也不能因为第 3 项停止完成所有可以离线实现和测试的工作。

用户的交付偏好是完成后提交、push、release。Codex 应先检查项目当前版本、tags、分支规则和既有发布流程：

- 范围内验证通过后自动创建 Conventional Commits，推送当前任务分支；不得擅自强推或覆盖标签。
- 按既有规则集成；需要 PR 时创建 PR，不绕过受保护分支。
- 在预期发布分支完成集成后，使用实际验证的 commit 创建相应 tag/release。未完成集成时不把分支成果包装成正式版本。
- 如果缺少真实账号验证，只能在规则允许时发布明确标记限制的 prerelease；不得标为三家生产验证完成。
- 没有既有发布流程时采用最小 GitHub prerelease 流程，不顺带开发 App Store/Play Store 发布系统。版本从实际 tags/pubspec 推导，不能覆盖既有版本。
- 推送、CI、合并或发布权限受阻时，报告已完成的 commit、失败步骤和下一条必要操作，不声称成功。

当范围内实现、文档与验证达到上述交付状态后停止，不继续补商店、新云厂商或管理 API。
